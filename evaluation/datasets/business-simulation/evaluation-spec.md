# 星澜科技业务仿真评测规范

## 数据文件

- `questions.json`：60 道带金标准的问题。
- `01` 至 `28`：被检索的业务文档。
- `README.md` 与本文件是说明材料，不应上传到评测知识库。

## 分组

- `development`：40 题，用于调整分块、召回、Top K、提示词和拒答策略。
- `test`：20 题，只在形成候选方案后运行，不应用于逐项调参。

不能因为测试集分数较低而把测试题移动到开发集。语料或金标准发生变化时，应提升 `corpusVersion` 或 `schemaVersion` 并保存旧结果。

## 金标准字段

每个用例包含：

- `id`：稳定且唯一的题号。
- `split`：`development` 或 `test`。
- `type`：单事实、精确标识、多事实、跨文档、边界、版本冲突、噪声鲁棒或拒答。
- `question`：发送给系统的原始问题。
- `answerable`：语料是否包含足够证据。
- `referenceAnswer`：人工编写的最小正确答案，不要求模型逐字匹配。
- `requiredEvidence`：支持答案所必需的最小证据列表；每项包含文件、二级标题和连续原文。
- `tags`：用于分组统计的稳定标签。

## 评分建议

检索层至少计算：

- 题级 Recall@K：所有必要证据是否进入返回来源。
- 证据项召回率：召回的必要证据项数除以全部必要证据项数。
- 来源精确率：返回来源中确实支持答案的比例。
- 多证据完整率：多事实题是否找齐全部必要证据。

生成层至少人工或独立评审：

- 答案正确性。
- 关键结论是否均由引用支持。
- 是否与证据中的数字、范围和时间边界冲突。
- 无答案题是否明确拒答，且没有用常识补造内部规则。

不能只用字符串相等评价答案。参考答案可以用于辅助判断，但引用支持和边界含义必须单独评分。

## 运行纪律

每次评测记录 Git commit、知识库内容哈希、分块配置、Embedding 模型、生成模型、查询改写策略、Top K、Reranker 及提示词版本。开发集可以重复运行；测试集应按里程碑运行并保留全部原始响应。
