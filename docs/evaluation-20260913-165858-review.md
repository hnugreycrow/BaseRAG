## 检索与数据质量观察

18 个成功请求各返回 4 个来源，共 72 个来源位置：

- 18 个来自本次上传的员工手册。
- 18 个来自另一份内容重复的员工手册。
- 36 个来自与问题无关的 Markdown 语法演示文档。

这意味着每个成功请求都消耗了一半来源位置给无关文档，另外两个有效来源又是重复内容。q002 中无关 Markdown 文档甚至排在两个手册来源之前。当前固定 Top K 且没有去重或相关度门槛，全库数据越多，上下文污染风险越高。

样例员工手册在本轮基本作为一个长分块被召回，单个片段同时包含多项政策。因而 19 个证据字符串命中不能证明系统能在真实长文档中准确定位细粒度章节。

## 稳定性观察

- q001、q002、q003 分别耗时 21131、29495、31712 ms，真实模型链路有显著长尾。
- q011、q012 连续返回 502，但原始产物只保存 PowerShell 的状态码文本，无法区分模型上游错误、超时、重试耗尽、熔断或应用异常。
- 评测失败分支没有保存 answerable、expectedEvidence 和模型信息，汇总时必须再次连接 `questions.json`，降低了单个产物的自解释性。
- 产物记录了生成模型，但没有记录 Embedding 模型、维度、Top K、上下文预算和配置版本，尚不能完整复现。

## 修复与复验顺序

1. 从后端日志结合请求时间定位 q011、q012 的 502 根因；让评测脚本保存错误响应体、requestId 和错误阶段。
2. 修复 q015 的边界条件理解问题，通过通用提示词或生成后校验改善“超过、至少、至多、恰好”等限定词，不对单个题目硬编码。
3. 使用隔离评测知识库，清除重复员工手册和无关 Markdown 文档；或者让评测请求显式限定知识库范围。
4. 增加内容哈希去重或检索结果去重，避免相同正文重复占用 Top K。
5. 扩充样例文档，使政策分布在多个真实分块中，再分别评估召回和生成质量。
6. 完整重跑 20 题并人工评分，不只补跑失败题；达到确认后的门槛再关闭阶段 1。
