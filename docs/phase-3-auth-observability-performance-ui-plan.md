# BaseRAG 第三阶段：认证、可观测性、性能与前端升级计划

## 1. 阶段目标

将当前本地单用户系统升级为具备多用户隔离、逐次问答追踪、统一产品界面和可量化性能优化能力的版本。

实施顺序如下：

1. 登录、账号管理与服务端数据隔离。
2. 问答链路可观测性与性能基线。
3. 问答速度优化及质量回归。
4. 全站视觉、交互与前端代码统一。
5. 完整安全、性能和回归验收。

本阶段仍只支持本地 `local` profile，不包含内网部署、HTTPS、反向代理和生产运维。

## 2. Sa-Token、Redis 与多用户隔离

### 2.1 认证基础设施

- 引入与 Spring Boot 4 对应的 `sa-token-spring-boot4-starter`，并统一锁定通过项目构建和 SSE 回归测试的 Sa-Token 版本。
- 在 Docker Compose 中增加仅绑定本机的 Redis 服务、健康检查和持久化卷。
- Redis 不可用时认证失败关闭，不允许绕过鉴权。
- Sa-Token 会话保存在 Redis，默认有效期为 8 小时、无操作有效期为 30 分钟，首期不提供“记住我”。
- 使用 HttpOnly 会话 Cookie，设置 `SameSite=Strict`；本地环境允许非 Secure，未来非本地环境必须启用 Secure。
- 登录或会话恢复时返回 CSRF nonce，并存入 Sa-Token Session；所有写接口和 SSE POST 必须携带 `X-CSRF-Token`。
- 登录失败按“标准化用户名 + 客户端地址”在 Redis 中限流，15 分钟内最多失败 5 次。

### 2.2 用户与账号管理

- 新增 `users` 表，包含用户名、显示名、BCrypt 密码哈希、`ADMIN/USER` 角色、启用状态、最近登录时间和审计时间。
- 不开放自助注册。管理员可以创建、禁用用户和重置密码。
- 禁用账号或重置密码后，立即注销该用户已有的 Sa-Token 会话。
- 首次启动通过环境变量创建首个管理员，不在迁移或代码中保存默认明文密码。
- 新用户和首次管理员都不自动建立知识库，由用户在知识库管理界面按需创建；已有知识库保持不变。

### 2.3 数据迁移与所有权

- 为 `knowledge_bases` 和 `conversations` 增加非空 `owner_id`。
- 迁移先将历史知识库和会话归属给保留迁移用户，应用首次初始化管理员时再统一转交，避免在 Flyway 中写入真实密码。
- 文档、版本、分块通过知识库归属校验；消息和生成尝试通过会话归属校验，不重复添加无必要的所有权字段。
- 所有 Mapper 和 Service 查询显式接收当前用户 ID，不依赖前端隐藏按钮或只传资源 UUID。
- 跨用户资源访问统一返回 404，避免泄露资源是否存在。
- 问答检索范围由服务端计算为当前用户拥有的知识库集合。前端传入的知识库 ID 只能进一步缩小范围，不能扩大权限。
- 新上传对象的 RustFS key 加入用户 ID 前缀；历史对象保留原 key，通过数据库所有权控制访问。

### 2.4 认证和账号接口

- `POST /api/auth/login`：验证用户名和密码，设置 Cookie，返回当前用户与 CSRF Token。
- `GET /api/auth/session`：恢复前端登录态并刷新 CSRF Token。
- `POST /api/auth/logout`：注销当前会话并清除 Cookie。
- `PUT /api/auth/password`：用户验证旧密码后修改自己的密码，并注销其他会话。
- `GET /api/admin/users`：管理员分页查询用户。
- `POST /api/admin/users`：管理员创建用户。
- `PATCH /api/admin/users/{id}/status`：启用或禁用用户。
- `PUT /api/admin/users/{id}/password`：管理员重置密码。

统一认证异常协议：未登录返回 401，角色不足返回 403，账号禁用返回稳定业务码，并继续沿用现有 `ApiResponse` 与 `requestId`。

## 3. 单次问答可观测性

### 3.1 数据模型

新增 `rag_runs` 和 `rag_stage_runs`：

- `rag_runs` 保存用户、请求、会话、回答版本、状态、执行模式、模型、候选数、证据数、降级标记、开始时间、首 Token 时间和完成时间。
- `rag_stage_runs` 保存阶段名、子问题 ID、执行序号、状态、输入输出数量、模型信息、错误码和耗时。
- Trace 不重复保存问题正文、回答正文、文档内容、认证信息或模型密钥，通过已有消息 ID 关联业务记录。
- Trace 默认保留 30 天，由定时清理任务删除过期记录。

### 3.2 观测阶段

每次问答至少记录以下阶段：

- 会话记忆加载、异步摘要。
- 问题规划、意图路由。
- 每个子问题的 Embedding 和数据库检索。
- 候选合并、去重和 Rerank。
- Prompt 组装。
- 最终模型请求、首 Token 和流式生成。
- 引用校验、引用修复和结果持久化。

同时定义两个首 Token 指标：

- `endToEndTtftMs`：请求进入后端到发送第一条非空 `delta` 的时间，反映用户真实等待。
- `modelTtftMs`：最终回答模型请求发出到收到第一段模型内容的时间，反映模型服务自身速度。

Trace 在问答开始时写入运行记录，各阶段先在内存收集，终态时批量落库，避免观测逻辑显著增加问答延迟。异常、取消和应用重启均需产生明确终态；没有返回内容的请求，其首 Token 时间保持为空。

### 3.3 查询接口与权限

- `GET /api/observability/rag-runs`：按时间、状态、模型、执行模式和用户分页筛选。
- `GET /api/observability/rag-runs/{id}`：查看单次问答阶段瀑布和降级信息。
- `GET /api/observability/rag-runs/summary`：返回请求量、成功率、降级率，以及总耗时和两类 TTFT 的 P50/P95。

普通用户只能查看自己的记录；管理员可以查看全局记录并按用户筛选。观测查询同样执行服务端所有权校验。

## 4. 问答性能优化

### 4.1 基线

- 使用固定模型、隔离评测用户和固定知识库，对现有 SSE 会话接口建立冷启动、热启动和连续请求基线。
- 客户端记录从请求发出到首个有效 `delta` 和完整回答结束的时间。
- 服务端记录各阶段耗时、两类 TTFT、模型、候选数、证据数、Prompt 大小、降级和错误信息。
- 固定测试配置、数据版本和模型候选顺序，保证优化前后结果可比较。

### 4.2 优化项

- 将当前请求内同步执行的会话摘要移出关键路径，改为回答完成后的异步任务；摘要尚未完成时仍传入完整的未摘要历史，不能丢失上下文。
- 增加可配置的简单问题快路径：
  - MCP 关闭、首轮、单一目标且不依赖历史时，直接生成单个知识检索子问题。
  - 明确问候、帮助和能力询问由保守白名单进入系统闲聊。
  - 多轮、复合问题、疑似指代、工具场景或判断不确定时继续走完整规划和路由。
  - 快路径必须记录执行模式，并保留配置开关。
- 为不同模型调用设置独立重试策略：
  - 可降级的规划、路由、摘要和重排不做网络重试。
  - Embedding 最多重试一次。
  - 最终回答只允许在尚未输出内容时重试或切换候选模型。
- 根据 Trace 对 Rerank 输入数、最终证据数和 Prompt 长度执行固定网格评测，选择满足质量不下降条件下 P95 TTFT 最低的配置。
- 保留当前共享 Java HTTP Client 和连接复用，增加模型请求发出、响应头到达和首内容事件计时，用于区分模型慢与本地流水线慢。
- 本阶段不引入消息队列、分布式追踪系统或未经数据证明的 pgvector ANN 索引。

### 4.3 性能退出门槛

- 固定评测集下，端到端 TTFT 的 P50 和 P95 均比基线至少下降 30%。
- 回答正确率、必要证据覆盖率和引用合法率不得低于基线。
- 观测写入带来的 P95 额外开销不超过 2%。
- 若快路径或 Rerank 调参未通过质量门槛，对应开关保持关闭，并保留对比报告。

## 5. 前端统一升级

### 5.1 视觉系统

沿用现有 BaseRAG 蓝靛基调，建立统一设计 Token：

- Ink：`#17233C`
- Cobalt：`#4263EB`
- Mint：`#68DFC5`
- Canvas：`#F4F7FB`
- Surface：`#FFFFFF`
- Danger：`#D96C5F`

正文使用 Inter、PingFang SC 和系统无衬线字体；数据、耗时和 ID 使用 IBM Plex Mono。统一字号、间距、圆角、阴影、状态色和动效时长。

产品标志性视觉采用“证据轨迹线”：聊天页用于表达回答与来源的对应关系，观测页复用为阶段瀑布时间轴，使视觉装饰直接服务于产品的可追溯性。

### 5.2 页面与交互

- 统一登录页、聊天页、知识库、模型、用户管理和观测页面的导航、标题、空状态、错误状态、加载骨架和操作反馈。
- 登录页突出本地知识工作区定位，不使用通用营销页布局。
- 观测详情采用“摘要指标 + 阶段瀑布 + 模型和候选明细”布局。
- 普通用户隐藏账号管理入口；观测页自动限定本人，管理员显示用户筛选器。
- 支持 360px、768px、1280px 三档布局，并完整支持键盘焦点、屏幕阅读标签和 `prefers-reduced-motion`。

### 5.3 前端代码整理

- 将体积过大的聊天视图拆分为会话侧栏、消息轮次、回答工具栏、输入框和来源面板等组件。
- 抽取认证、SSE、分页和 Trace composable，避免页面组件直接重复处理请求生命周期。
- 新增认证 Pinia store、全局路由守卫和 401 自动回登录。
- Axios 与原生 SSE fetch 统一携带 Cookie 和 CSRF Header。
- 将通用设计 Token 放入全局样式，将知识库、聊天和观测的专用样式保留在对应模块，减少选择器互相覆盖。

## 6. 测试与验收

### 6.1 认证与安全

- 覆盖登录成功和失败、Cookie 属性、CSRF、注销、密码修改、失败限流和账号禁用。
- 覆盖 Redis 重启后会话恢复，以及 Redis 故障时拒绝认证。
- 验证 Sa-Token 过滤器支持 `SseEmitter` 异步请求；问答、停止、重试、重新生成和断连行为不得回归。
- 使用两个用户执行跨用户负向测试，确保无法读取、修改、删除或检索对方的知识库、文档、会话、消息、生成任务和 Trace。
- 验证历史默认知识库、文档和会话全部转交首个管理员，已有文件仍可下载和检索。

### 6.2 可观测性

- 成功、失败、取消、降级、模型回退、无 Token 和引用修复分别产生正确的 run 与 stage 数据。
- 每次运行只能记录一次首 Token；没有有效内容时保持为空。
- 验证普通用户和管理员的查询范围及筛选统计结果。
- 验证观测数据不包含问题正文、回答正文、文档内容、Cookie、Token 或 API Key。

### 6.3 前端与性能

- 覆盖路由守卫、会话恢复、CSRF 注入、权限菜单、Trace 筛选和 SSE 解析。
- 完成桌面和移动端截图检查、键盘操作检查与 reduced-motion 检查。
- 固定数据集至少执行三轮冷、热对比，输出阶段耗时、两类 TTFT、总耗时、质量和错误率报告。
- 最终运行后端测试和 Spotless、前端 Vitest、Prettier 检查与生产构建。

## 7. 默认范围与非目标

- 本阶段支持多用户私有数据，不增加共享知识库、组织、团队或细粒度 RBAC。
- 普通用户管理自己的知识库和会话；管理员额外管理账号并查看全局观测数据。
- 问答默认检索当前用户拥有的全部 READY 知识库，暂不增加用户手动选择检索范围的 UI。
- Redis 首期只承担 Sa-Token 会话、CSRF 和登录限流，不保存问答正文或文档内容。
- 不开放注册，不提供邮件找回密码流程，不改变当前本地部署边界。
- 完成后同步更新 `REQUIREMENTS.md`、架构文档、决策记录、环境变量示例和启动说明。
