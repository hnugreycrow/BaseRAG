# 阶段 1 验收分析

评估日期：2026-09-13。

## 结论

阶段 1 的主体功能和工程链路已经完成，可以判定为“工程实现基本通过”。2026-09-13 已完成首轮真实模型评测，但结果没有达到本文件建议的关闭门槛，因此还不能判定为“阶段 1 正式验收通过”。当前建议状态为：**工程有条件通过，质量验收未通过**。

这个结论区分两件事：自动化测试能够证明代码、协议、数据库、对象存储和检索链路按预期工作，但不能证明真实模型的召回、回答忠实性和拒答质量达标。

## 首轮真实模型评测结果

评测产物为 [`evaluation-20260913-165858.json`](../.artifacts/evaluation-20260913-165858.json)，生成模型记录为 `qwen-plus-latest`。逐题人工复核见[评测审阅记录](evaluation-20260913-165858-review.md)。

| 指标 | 结果 | 建议门槛 | 判定 |
| --- | --- | --- | --- |
| 系统/API 成功率 | 18/20（90%） | 20/20 | 未通过 |
| 有答案题必要证据完整召回 | 14/16；按证据项计 19/22 | 至少 15/16 | 未通过 |
| 有答案题回答正确 | 13/16 | 至少 15/16 | 未通过 |
| 无答案题正确拒答 | 4/4 | 4/4 | 通过 |
| 与来源冲突的关键结论 | 1（q015） | 0 | 未通过 |
| 引用编号可追踪 | 18 个成功响应均合法 | 100% | 通过 |

延迟方面，20 个请求的 P50 为 2321 ms、P95 为 29495 ms、最大值为 31712 ms。前三题分别耗时约 21.1、29.5 和 31.7 秒，说明真实模型链路存在明显长尾；两个 502 结果只记录了 HTTP 状态，没有错误响应体、requestId 或服务端阶段耗时，因此不能从产物中确定根因。

本轮在已有全库数据上执行，不是干净知识库。18 个成功响应共返回 72 个来源位置，其中 36 个来自无关的 Markdown 语法演示文档；另外两份员工手册内容重复，各占 18 个位置。换言之，每次成功请求都返回了两份重复的手册片段和两个无关片段。它证明了全库检索链路可以运行，但会高估证据命中，并暴露出重复文档、无关召回和上下文浪费问题。

员工手册在本轮被合并为覆盖大部分内容的单个长分块，因此 `expectedEvidenceMatched` 更接近“整份手册是否进入 Top K”，不足以证明细粒度分块的排序质量。该指标仍不能替代 Recall@K 或人工判断。

## 已经被证明的能力

- 模型服务协议不是只依赖 Mock 方法调用：测试覆盖了实际 HTTP 路径、认证头、请求字段、响应解析、429/5xx 重试、超时和异常响应。
- 文档数据链路连接了真实 PostgreSQL、pgvector 和 RustFS，而不是内存数据库或文件存储替身。
- 返回给前端的 `sources` 是进入生成上下文的完整片段，并且可以追踪到知识库、文档、版本和数据库分块。
- 事务测试覆盖了分块写入中途失败，避免半成品索引被标记为 READY。
- 不同 Embedding 模型和维度不会被静默混用。

## 尚未通过的能力

### 1. 真实检索效果

首轮结果中，所有成功的有答案题都召回了必要证据，但 q011、q012 因 API 失败没有完成检索与回答；重复的整份手册片段又使证据命中过于容易。仍需在干净、非重复并包含多个有效分块的数据集上验证单事实、多事实、标识符和否定问题。全库存在多个向量模型时，不同模型的相似度分数是否适合直接合并排序，也仍需要实际数据验证。

### 2. 真实回答忠实性

首轮真实模型已出现明确反例：q015 的来源写的是“超过 2 个工作日未处理时”才可催办，回答却得出“审批两天没处理可以催办”。引用编号合法只说明编号存在，不能说明回答正确理解了来源中的边界条件。

### 3. 无答案拒答质量

首轮中工资、CEO、产假和未来政策四类问题均正确拒答，单次结果达到 4/4。由于检索仍固定返回低相关片段，拒答主要依赖生成模型判断；后续应通过重复运行和扩充无答案题确认稳定性。

### 4. 明确的质量门槛

现有验收说明要求人工检查，项目负责人尚未正式确认数值门槛。本文件使用下方建议门槛做本次判定，避免将“已经生成 JSON”误当作“验收通过”。

## 阶段 1 关闭条件

以下条件全部满足后，才能把阶段 1 状态改为“正式通过”：

1. 使用计划投入实际环境的生成模型和 Embedding 模型，在干净、没有重复样例和无关文档污染的开发知识库重新执行 `scripts/evaluate.ps1`。
2. 20 个问题全部得到有效 API 响应，没有导入、向量化、检索或生成服务错误。
3. 对每题分别记录“必要证据是否进入 sources”“回答是否正确”“关键结论是否由引用支持”“无答案题是否正确拒答”。
4. 保存 `.artifacts/evaluation-*.json` 和人工评分汇总，记录生成模型、Embedding 模型、维度、主要 RAG 参数和执行时间。失败项也必须保留 answerable、expectedEvidence、响应体、requestId 和错误阶段，使结果可复现、可诊断。
5. 在桌面和 390 像素宽度下完成一次真实链路浏览器复验：上传、开始分块、状态变化、单事实问答、多事实问答、无答案问答、来源展开和错误提示。

## 建议的通过阈值

下面是建议门槛，不是当前项目已经确认的标准；开始真实模型验收前应由项目负责人确认：

| 指标 | 建议门槛 |
| --- | --- |
| 系统/API 成功率 | 20/20 |
| 16 道有答案题必要证据召回 | 至少 15/16；多事实题必须召回全部必要证据 |
| 16 道有答案题回答正确 | 至少 15/16 |
| 4 道无答案题正确拒答 | 4/4 |
| 与来源冲突的事实或无依据的关键结论 | 0 |
| 引用可追踪到实际上下文 | 100% |

若未达到门槛，应保留评测结果，先判断问题属于分块、召回、上下文选择、提示词还是生成模型，再有针对性地调整，不能仅靠重复运行挑选最好的一次结果。

## 不属于阶段 1 的缺口

登录与权限、PDF、异步任务、消息持久化、多轮对话、流式输出、正式部署和高可用均已明确排除在阶段 1 之外，不应据此否定阶段 1；这些能力进入[阶段 2 计划](phase-2-plan.md)。
