# 阶段 2 计划：内部 Beta

> 状态说明（2026-09-13）：本文是历史路线图，不是当前产品范围。其中会话持久化、SSE、多轮问题改写、停止、重试、重新生成和来源快照已经落地。当前支持范围以 `../REQUIREMENTS.md` 为唯一来源；继续实施本计划前，应先重新整理剩余事项与里程碑。

## 阶段目标

阶段 2 将 JAgent 从“可演示的单轮 RAG”升级为“可供小范围真实用户持续使用的内部 Beta”。重点不是扩大 Agent 能力，而是让现有 RAG 系统具备稳定性、可评测性、可恢复性、数据隔离和基本运维能力。

阶段 2 不接收阶段 1 的未完成验收。开始开发前，应先满足[阶段 1 验收分析](phase-1-acceptance.md)中的关闭条件并冻结一份真实模型质量基线。

## 范围和优先级

### P0：会话、流式回答与持久化

- 使用 SSE 输出回答增量、完成事件和结构化错误；断开连接后及时取消不再需要的生成请求。
- 将会话和消息保存到 PostgreSQL，刷新页面后可以恢复。
- 支持新建、重命名、删除和搜索会话。
- 支持停止生成、失败重试和重新生成，并明确每次生成所使用的用户问题、来源和模型。
- 支持多轮追问。检索使用当前问题和必要历史生成独立检索问题，生成上下文只保留受预算约束的相关历史，避免历史无限增长。
- sources、citations 和 modelInfo 与 assistant 消息一起持久化，历史回答可以复核当时证据，不因后续重新分块而失去审计信息。

### P0：异步文档处理与任务恢复

- 将分块和向量化从同步 HTTP 请求改为持久化后台任务；创建任务后立即返回 taskId。
- 记录 QUEUED、PROCESSING、READY、FAILED、CANCELLED 状态，以及进度、开始/结束时间、失败代码和可读错误。
- 管理端展示进度，并支持失败重试和取消尚未完成的任务。
- 通过数据库原子认领任务，应用重启后能够识别并恢复超时的 PROCESSING 任务。
- 重试需要幂等：同一任务不会产生重复分块，不会把旧任务结果覆盖到更新版本。
- 首期使用 PostgreSQL 任务表和受控工作线程即可；在单实例内部 Beta 阶段不强制引入 Redis 或独立消息队列。

### P0：用户身份与数据隔离

- 增加用户、会话和登录状态，密码使用可靠的单向哈希；Cookie 采用 HttpOnly、SameSite 和适合环境的 Secure 策略。
- 知识库、文档、任务和会话都绑定所有者，所有查询和写操作在服务端校验访问范围。
- 将当前默认“检索全部知识库”改为“检索当前用户明确选择的知识库”；不能只依赖前端传入的 knowledgeBaseId。
- 后台管理 API 与普通问答 API 分权，记录创建、删除、重新索引等关键操作。
- 增加跨用户读取、修改、删除和检索的负向测试。

### P1：检索质量与评测体系

- 将 20 题脚本升级为可重复评分的评测流程，分别输出召回、答案、引用和拒答结果，而不是只记录字符串命中。
- 建立 Recall@K、必要证据覆盖率、回答正确率、引用支持率、拒答准确率、P50/P95 延迟和单题模型成本基线。
- 增加关键词召回并与向量召回融合，改善邮箱、编号、数字和专有名词问题。
- 对候选片段去重，避免重叠分块占满上下文预算。
- 在基线证明有收益后再引入 Reranker；必须记录质量增益、额外延迟和费用。
- 为低相关度结果建立经过评测校准的拒答策略，不能仅凭任意固定阈值上线。
- 多种 Embedding 模型并存时，验证分数是否可比较；必要时按模型归一化、分别取候选后重排，或者限制一次问答使用的知识库模型组合。

### P1：文档能力

- 支持文本型 PDF，保留页码和标题等来源定位信息；扫描件 OCR 暂不纳入本阶段硬性范围。
- 通过内容哈希识别重复上传，并让用户选择复用、创建新版本或取消。
- 增加文档版本替换和索引重建，切换成功前继续使用旧 READY 版本。
- 支持批量上传、批量删除和批量重建索引，并显示每个文件的独立结果。
- PDF 之后再评估 DOCX；只有能够稳定提取正文、结构和来源位置时才纳入验收。

### P1：可观测性、成本与部署

- 为请求和后台任务建立统一 trace/request id，使用结构化日志记录关键阶段，不记录密钥和完整敏感正文。
- 记录检索、重排、首 Token、生成和总耗时，以及候选数量、上下文长度、Token 用量、模型和估算费用。
- 提供应用、数据库、RustFS 和模型服务的健康检查；区分依赖不可用、限流、超时、配置错误和业务校验失败。
- 增加数据库与 RustFS 的备份、恢复和一致性检查说明，并实际做一次恢复演练。
- 提供可重复的内部环境部署配置、迁移步骤、回滚方案和密钥管理方式；移除只能在 local profile 启动的限制，但不直接开放公网。

## 里程碑

| 里程碑 | 交付结果 | 退出条件 |
| --- | --- | --- |
| M0：阶段 1 关闭 | 真实模型评测基线和人工评分报告 | 阶段 1 关闭条件全部满足 |
| M1：异步索引 | 持久化任务、进度、取消、重试、重启恢复 | 故障注入后无重复索引、无永久 PROCESSING |
| M2：可持续对话 | SSE、会话持久化、多轮检索、历史来源审计 | 刷新可恢复，会话隔离，断流和重试行为明确 |
| M3：身份与隔离 | 登录、所有权、知识库选择和授权校验 | 跨用户负向测试全部通过 |
| M4：质量升级 | 自动评测、混合召回、去重，按收益决定 Reranker | 质量达到本阶段门槛且回归可重复 |
| M5：文档与运维 | PDF、版本、批量操作、监控、备份恢复、内部部署 | 完成端到端验收和恢复演练 |

M1 与 M2 可以在数据库模型确认后并行开发；M3 必须在内部 Beta 引入真实用户数据前完成；M4 的算法选择必须建立在 M0 基线上；M5 的 PDF 批量处理依赖 M1 的异步任务能力。

## 数据模型与接口方向

阶段 2 预计新增或扩展以下核心对象：

- users：用户身份与状态。
- conversations、messages：会话、消息、生成状态和当时的引用快照。
- ingestion_jobs：文档处理任务、租约、进度、重试次数和错误。
- document_versions：扩展 MIME 类型、内容哈希、来源页码与版本切换信息。
- evaluation_runs、evaluation_results：评测配置、模型参数、逐题结果和人工评分。
- audit_events：关键管理操作，不保存密钥和不必要的正文。

接口应保持资源边界清晰：会话下创建消息，文档版本下创建索引任务，问答请求显式携带允许检索的知识库集合。流式接口的事件格式需要版本化，并为完成、取消和错误定义终态。

## 阶段 2 验收标准

### 功能

- 用户可以登录，上传 Markdown 或文本型 PDF，并观察异步处理直至可检索。
- 用户可以选择一个或多个自己有权访问的知识库进行问答。
- 回答流式显示，刷新后会话、消息、来源和生成状态仍然存在。
- 支持至少一类需要上下文的追问，同时不会把无关历史全部发送给模型。
- 文档能够创建新版本并原子切换索引；旧回答仍能显示当时的来源快照。

### 稳定性与恢复

- 文档处理期间重启应用，任务可以自动恢复或进入可重试终态，不永久卡在 PROCESSING。
- 对模型限流、超时、无效响应、数据库异常和 RustFS 异常均返回可识别错误，并产生可追踪日志。
- 重复提交、任务重试和网络重试不会生成重复有效版本或重复消息。
- 备份恢复演练能够恢复数据库元数据与对应原文件，并通过一致性检查。

### 安全与隔离

- 用户不能通过猜测 UUID、修改请求参数或全库问答读取其他用户的知识库、文档、分块、任务和会话。
- 未登录请求、越权管理请求和跨用户检索均有自动化测试。
- 日志、API 响应和前端构建产物不包含模型密钥、数据库密码或对象存储凭据。

### 质量与性能

- 固定评测集、模型版本和 RAG 参数后，评测报告可重复生成，并能与阶段 1 基线对比。
- 质量门槛至少不低于阶段 1 的最终通过结果；混合召回或 Reranker 只有在整体指标改善且回归通过时启用。
- 为上传、检索、首 Token 和完整回答设定可观测的 P95 目标。具体数值应在 M0 基线测量后冻结，避免凭空制定。
- 每次回答可以追踪使用的知识库、来源、模型、Token、耗时和估算费用。

## 明确不做

以下内容不属于阶段 2，避免内部 Beta 被扩展成开放式 Agent 平台：

- 通用工具调用、浏览器操作和任意代码执行。
- 多 Agent 编排、可视化工作流和插件市场。
- 联网搜索与知识库外部自动补充事实。
- 复杂组织架构、计费系统和面向公网的多租户商业化部署。
- 扫描 PDF 的通用 OCR、图片理解、音视频处理。
- 在缺少规模和性能证据时提前引入分布式消息队列、缓存集群或近似向量索引。

## 主要风险

- 当前全库检索与用户数据隔离存在天然冲突，必须先把检索范围变成服务端授权后的集合。
- 知识库使用多种 Embedding 模型时，每次提问的向量请求数、成本和延迟会随模型种类增长，且相似度未必可直接比较。
- 多轮历史会同时影响检索问题和生成上下文，若没有独立预算和回归集，容易降低单轮问题质量。
- PDF 提取的阅读顺序、表格和页码定位不稳定，必须限定首期支持范围并保留原文件定位。
- 异步任务的难点是幂等、租约和版本切换，不是简单地把同步方法放进线程池。
